# Reflection

## 1. The hardest bug I hit this week, and how I debugged it
The hardest bug was getting Supabase writes and shareable reports working from a static HTML frontend. At first, the lead save failed with a generic “could not save” message. My first hypothesis was that the Row Level Security policy was wrong, so I checked the insert policy for the `leads` table. Then I opened the browser console and saw a 404-style Supabase request failure. That changed my hypothesis: the problem was not only RLS, but also the API URL. I had used a URL with `/rest/v1/` in it, but `supabase.createClient()` expects only the base project URL. After changing the URL to `https://PROJECT_REF.supabase.co`, inserts started working. Later, I tested public report URLs in incognito to confirm that the report was actually loaded from Supabase and not from local browser state. That test was important because it proved the viral/share loop worked for a fresh visitor.

## 2. A decision I reversed mid-week, and what made me reverse it
I initially treated every recommendation as a “savings” recommendation. For example, if a small team was using Copilot Enterprise, I recommended Copilot Business. But when the user-entered current spend was lower than the calculated Business price, the app showed a recommendation that increased spend while still acting like an optimizer. That was not finance-defensible. I reversed the decision and changed the audit engine so recommendations that do not create direct savings become “review fit” recommendations instead of savings claims. This made the product more honest. A finance person should not feel tricked by the tool. If the entered spend does not support savings, the app now says no direct savings were found and still explains possible governance or plan-fit concerns.

## 3. What I would build in week 2 if I had it
In week 2, I would move the app from a mostly static frontend into a cleaner production architecture. First, I would add a Vercel serverless function for the AI-generated summary using Anthropic, with the API key stored in environment variables. Second, I would add Resend for transactional email so users receive their report link and high-savings users get a Credex follow-up message. Third, I would migrate the frontend to Next.js so each shared report can have dynamic Open Graph metadata and clean routes like `/report/[shareId]`. I would also unify the audit engine so the browser and tests import the same source of truth. Finally, I would add stronger abuse protection, rate limiting, and better pricing update workflows so the tool stays accurate over time.

## 4. How I used AI tools
I used AI tools mainly for implementation guidance, debugging, and documentation drafting. I used them to reason through Supabase setup, RLS policies, Vercel deployment, test structure, and markdown deliverables. I did not trust AI with final pricing numbers without checking official sources, because pricing changes frequently and inaccurate prices would damage the credibility of the audit. One specific time the AI guidance was incomplete was around Supabase URLs: the app failed because the URL included `/rest/v1/`, which is not the format expected by `supabase.createClient()`. I caught it by checking the browser console and request failure. That reinforced that AI help is useful, but debugging still needs direct observation and verification.
